## Delivered design

The **six current conditions × two natural-language datasets × three data realizations × five orders give 180 core cells**, each with a 1,000-edit stream. The document's newer five-order instruction is used; the older approximate budget in plan 9 used two orders. The draft adds conditional study slots without pretending their implementations or gates are complete: 19 distinct condition definitions, 570 natural-language cells, and 90 synthetic composition cells, **660 cells inclusive**. These are planning records, not approved jobs.

Each cell has a logical identity, checkpoint references, dataset/realization/order/model seeds, paired-analysis key, unique result and checkpoint destination templates, token estimates with unknown exact values explicitly null, phase-separated expected base calls, memory/time ceiling proposals, a failure reserve, checkpoint schedule, endpoint list and admission gates. All `launch_allowed` and ceiling `frozen` fields are false. Logical cell IDs are draft indexing keys; the eventual `<freeze-id>` must bind the selected checkpoint/config/source/data identities. A changed condition cannot reuse an old frozen attempt path.

The checkpoint registry reuses original BP, random-reader and existing learned-reader resources by path and SHA256. `cf_pool3k_pair_own_400` is an identified development candidate, **not the final learned selection**; its null threshold remains pending. Future BP/ePC base training, caps, unroll, settling and continuation checkpoints are explicit placeholders. Shared training is billed once in `shared_training_jobs`, not once per order or appearance in a comparison.

### Conditions, comparisons and reuse

- **Current core:** v0 live C1 and C2; v0-stable C1; matched-update C1; R1-nonlearned random tied reader with cosine gate; learned feedforward reader with trained pairwise null. The proposed matched-update rule uses five steps at 0.1 to match the current delta-step setting; available historical matched ledgers used three steps, so exact cost/behavior parity remains a profiling gate.
- **Matched base-training table:** BP-old / BP-feedforward and ePC-old / ePC-feedforward add four conditions. The original-base old/feedforward cells are reused in both 2 × 2 comparisons. Original GPT-2 is not relabelled as an episode-trained base. Cap-only BP/ePC pilots do not implement the requested base-training conditions.
- **Estimator reference:** one fixed-fast-unroll reference cap on the original base. This condition is unimplemented, so its absence cannot support a negative claim about unrolled learning.
- **Stage 3, conditional on a working Stage 1–2 cap:** one development-selected nonzero settling count from 1/4/8, parameter-matched feedforward and compute-matched recurrent controls. The zero-step row is reused only if its architecture, parameter values and configuration are identical to the selected feedforward cap; otherwise add a separate zero-step condition before freeze. The illustrative ePC base binding must be replaced if another base is selected. There is no authorization here to select a winner on confirmation outcomes.
- **Continuation:** literal self-teacher KD and an informative LM-continuation treatment, each evaluated with stable and learned caps. Original controls are reused. LM continuation is the lead-queue default proposal; its formal decision, token budget, parameter-change mask and implementation remain to be recorded. Literal KD is a numerical negative control. Learned caps are held fixed in these continuation rows; this is a declared transfer test, not cap retraining.
- **Memory frontier:** learned feedforward at the v0 38,535,168-byte ceiling, alongside the shared v0-stable/matched cells. Core R1 uses the plan's 64 MiB total persistent ceiling; the default core comparison alone is not memory-matched.
- **Composition:** six conditions × 3 × 5 in the newly reserved synthetic physical namespace. This remains conditional on generator/model compatibility and a lead-emitted fresh dataset. A new legacy seed alone does not satisfy the current namespace contract.

The named learned-vs-random comparison changes both training and gating/null behavior. It measures the full deployed package; it is not by itself a causal isolation of learned parameters. If that stronger claim is intended, the owner must add a matched architecture/gating ablation and its resource price before freeze. Likewise, equal adaptation step counts do not prove equal full/partial-pass compute.

This matches the plan's three-cluster analysis language but must be explicitly confirmed before freeze. Three order repeats are not three independent training seeds. Exact stream tokens cannot be calculated before final data preparation, so the draft leaves them null. The zsRE support-position proxy uses 11.0184 prompt + 3.7143 answer-with-newline tokens per clear candidate; CounterFact uses the 300-item development pool. These are workload proxies, not exact valid training-pass tokens, and cannot certify token matching between methods.

## Costs and the budget decision

**The 15-hour confirmation envelope is not supported by this expanded draft.** Core provisional ceilings total **149.7 hours including 20% failure reserves**. This is a planning stress estimate, not measured GPU consumption or a prediction that every run takes its ceiling. It makes the scope/budget conflict visible rather than quietly shortening streams, omitting endpoints or dropping realizations.

| Core condition | zsRE seconds per cell: ceiling + failure reserve | CounterFact seconds per cell: ceiling + reserve | All 30 cells including reserve |
| --- | ---: | ---: | ---: |
| `v0_live_C1` | 3,420 + 684 | 3,420 + 684 | 34.2 h |
| `v0_live_C2` | 1,860 + 372 | 1,860 + 372 | 18.6 h |
| `v0_stable` | 3,660 + 732 | 3,660 + 732 | 36.6 h |
| `matched_update` | 2,940 + 588 | 2,940 + 588 | 29.4 h |
| `R1_nonlearned` | 1,620 + 324 | 1,560 + 312 | 15.9 h |
| `R1_learned_ff` | 1,560 + 312 | 1,440 + 288 | 15.0 h |

Cost construction is explicit in the builder. For each condition/dataset, historical 100-edit observations provide phase counts and wall/learning-time rates. The illustrative point proxy is:

`1000 × learning seconds/edit + 1400 × max(0, wall seconds/edit − learning seconds/edit) + 200 × wall seconds/edit + 780 seconds`.

The first term prices update work, the second crudely allows for checkpoint/query work at 100/300/1000, the third is a challenge proxy, and 780 seconds is a historical full-split drift allowance. The proposed ceiling rounds 1.25 × that sum up to a minute; a separate 20% retry/failure reserve is then added. The 25% headroom and 20% reserve serve different purposes. Occupancy, decode lengths, compilation and phase-accounting defects mean none of these coefficients is a freeze-quality measurement.

In particular, 780 seconds is the old ~13-minute full-split proxy, **not a new GPU profile**. Repeated across 180 adapted states, that term plus headroom/reserve alone accounts for 58.5 hours. P2 must replace it with the exact endpoint workload and measurement. CounterFact costs for v0 and matched controls borrow zsRE rates and are labelled unprofiled; historical matched costs are for three steps; conditional conditions borrow only a profile family, not a measured implementation. Full, partial and reverse calls are kept separate. Do not add their counts as interchangeable operations or compare raw reported token counters as exact compute.

The inclusive 660-cell sum is 1,244.7 hours **because most future conditional cells carry an arbitrary 7,200-second placeholder ceiling**. It is not an estimate of their performance and should not be presented as one. Their training ceilings are unknown. The two profiling jobs themselves propose 5,400 seconds total, separately priced. Eleven completed nonzero-step pilot summaries report 47,598.37 seconds (13.22 hours) of training wall time; that inventory is descriptive and is neither the project's total GPU charge nor a remaining budget. The legacy 100-step pilot lacks `args.tag`; the proposed compatibility fix uses its directory name. Zero-step evaluation summaries do not enter the completed training total.

Decision after profiling: retain the required core and enlarge the allocation, or record an explicit scope/endpoint amendment supported by the lead. Conditional work is admitted only after its scientific gate and own price are known. Shared checkpoints/contrasts are already deduplicated; apparent savings from reusing historical outcome scores are not valid fresh-data comparisons.

## Exactly two profiling jobs for the orchestrator

**P1-edit-memory — proposed 1,800-second job.** Execute ten edits for each of the six current conditions on both datasets, measuring empty and occupied memories at 0/100/300/1000. Use existing development data only. Where 1,000 unique development records are unavailable, use clearly labelled duplicate-key stress fixtures for capacity/throughput; those fixtures do not measure generalization or representative semantic retrieval. Profile the exact five-step matched-update rule and exact selected deployment settings. Record cold compilation separately from warm p50/p95/max; full/partial/reverse calls and valid tokens; failed edits and rollback work; persistent logical bytes, RSS and device peak; restore hash/byte equality; returned costs versus ledger and instrumented base-call deltas; answer-length buckets. This is one multi-case profiling job, not one ten-edit cell. Extend it for later implementations before admitting their conditions.

**P2-outer-endpoint — proposed 3,600-second job.** Execute two matched outer updates on four development episodes for BP cap and ePC-credit cap estimators, using identical examples, masks and seeds. Profile endpoint queries at occupancies 100/300/1000, 100 near-miss queries, 50 independent revision clones and 32-token maximum decoding. Use 128 windows of 128 tokens for the small drift assay (16,256 scored next-token targets), then measure the declared full-split endpoint on all complete validation windows with an explicit dropped-tail rule. Count passes inside JIT/unroll, failed work and compilation; record actual phase token masks and device time, base-leaf change masks, query resets, full-split time and maximum in-flight budget overshoot. Fixed-unroll, matched base BP/ePC, self/LM continuation and settling controls require later extensions of this same profile specification; a current cap-only profile does not price an unimplemented base-training path.

Neither profile has run in this lane. Both require a lease, GPU availability and the applicable R1-X3 repairs. Their proposed job durations are admission proposals, not authorized frozen limits; a profile that cannot complete must stop with costs recorded and be replanned before final ceilings are chosen.

## Execution checkpoints and analysis contract

1. **CPU-ready checkpoint:** validate source hashes, unique physical cells/destinations, shared-checkpoint registry and paired contrast coverage. Done for this draft.
2. **Data-ready checkpoint:** reviewed E.2-eligible fresh data; subject/context separation; source/hash/token identities; independent lead sealing. Pending.
3. **Implementation/selection checkpoint:** select learned checkpoint and null threshold on development only; implement or explicitly defer unroll/base-training/continuation/settling; pin parameter masks and objective conventions; resolve zero-step identity and RNG axes. Pending.
4. **Contract checkpoint:** repair/re-audit capacity, actual byte accounting, query boundaries, cost reconciliation, failure reasons and complete preflight admission. See `logs/audit_r1_26.md`. Pending.
5. **Profile checkpoint:** execute P1/P2; replace all borrowed rates and placeholders for admitted conditions; include checkpoint, near-miss, revision, drift, failure and retry costs; report exact pass tokens and memory peaks. Pending.
6. **Freeze checkpoint:** lead chooses scope/budget, primary comparisons/multiplicity, checkpoints, margins, token/decode policies and paired inventory, then creates the versioned revision freeze. The old v0 freeze does not authorize this draft.
7. **Run checkpoints:** maintain 1,000 edits and rescoring at 100/300/1000. Record immediate full-answer ES, unconditional RET-ES/RET-GS/LS, explicit near-miss and revision tests and endpoint fidelity. Survival-conditional results are diagnostics. Revision scenarios use independent clones so they do not silently alter the primary stream; challenge records need final definitions and their own identities before freezing.
8. **Analysis checkpoint:** pair by item/order and cluster by realization with all orders together; label intervals preliminary with only three clusters. Proposed practical RET-GS gain is +0.05 with the paired interval above zero, alongside ES −0.02 / LS −0.01 margins and KL ≤ 0.001 nats / loss increase ≤ 0.01. Missing pairs and resource failures are not imputed as outcomes. Freeze the exact classification and multiplicity rule before final results.
9. **Failure checkpoint:** stop the queue on correctness failures; charge failed work and every retry with a fresh attempt identity. The 20% reserve is not permission to overwrite attempts or tune using confirmation results.
