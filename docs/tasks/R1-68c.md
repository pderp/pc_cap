# R1-68c — phase timing and batched drift

Status: implementation/CPU validation complete; real-base parity and re-profile are owner gates. Agent: Codex.

Inputs: the measured v5 full/incremental cells, existing R1-68b driver/runtime, installed RevisionCap and BPBase batch kernels. Outputs: `scripts/r1_68c_dev_cell.py`, `scripts/r1_68c_batched_drift.py`, `scripts/r1_68c_rebind_recipe.py`, `tests/revision_v1/test_r1_68c_driver.py`, and `docs/tasks/R1-68c-zsre-v5-{full,incremental}.recipe.json`. All are new files; installed sources, old recipes and drivers are unchanged.

The new driver is hash-pinned to R1-68b and selected by its own recipe source bindings. `integrity_profile=full` retains scalar assays and defensive clones. `incremental` omits the outer clone/restore for immediate checks, retention, locality, unseen and drift, retaining full state-hash comparisons around those read-only phases and immutable identity checks. Edit phases retain incremental inventory accounting; challenge/composition phases retain their defensive snapshots. A read-only mutation stops the cell without a checkpoint receipt. Its possibly corrupted in-memory object must be discarded; resume reconstructs from the last verified durable checkpoint. No successful same-phase restore is claimed for a deliberately clone-free phase.

Each phase now separately measures recipe verification, immutable identity verification, state hashing, clone, restore, model/assay operation, and phase-file writes. Completed file-write timings live in new `phase-timings/` records outside the hash-checked journal. Timing-record and checkpoint-file writes are explicitly excluded from that component; overall attempt wall time still includes them. Failed operation time and ledger deltas remain retained.

**The existing attribution needs qualification.** R1-68b's incremental edit and immediate phases already used `snapshot=None`; it did not clone/restore them. Therefore the residual ~545 s cannot be assigned specifically to those outer clones from the prior aggregate timers. `verify_inputs()` and repeated `adapter.identity()` still rehash installed inputs, reader parameters and base weights. This revision instruments those costs without weakening their checks. Inner endpoint checks/clones remain inside operation time. The owner re-profile should identify the dominant measured component before proposing another change.

The installed learner's `last_logits_batch` was a list comprehension. The new `PositionBatchReader.last_logits_batch` uses the existing production JAX batch kernels. It runs an unedited batch, supplies each result to one fresh `selection_for` call through a shallow read-only view, computes the same prompt-position write, and performs corrected partial forwards in batches. Nested prefixes never inherit a shorter prefix's selection. Cap-off values reuse the same unedited passes; original-base values remain separately labelled. Hard-null rows return the unedited logits exactly. Controller-only, explicit-delta, single-site and hard-null cases are tested.

Batches are grouped by context-length bucket, with a recipe-bound maximum of 1–32 (default 16). Physical padding rows and any extra partial forwards are charged, and returned counters remain separate from shared-ledger accounting. There is no retained collection of all 16,256 hidden states: hidden arrays are bounded by one batch. Batch arithmetic may differ by floating-point roundoff. Per-position NLL tolerance is 2e−5 absolute/2e−6 relative in TinyBase tests, rather than a false promise of bitwise logits across scalar and batched kernels. Gate decisions near a threshold require real-base comparison before operational admission.
