## Interface

```python
from pccap.revision_v1.endpoints import EndpointEvaluator, load_dev_challenges, summarize

doc, source_binding = load_dev_challenges()
evaluator = EndpointEvaluator(cap, tokenizer, max_new=32, ledger=ledger)
# Owner runs these against a deliberately chosen starting memory state.
near_rows = [evaluator.near_miss(row) for row in doc["near_neighbour"]["items"]]
near_summary = summarize(near_rows, "preserved")
revision_rows = [evaluator.revision(row) for row in doc["temporal_correction"]["items"]]
revision_summary = summarize(revision_rows, "revision_success")
```

The evaluator itself writes no files, loads no base, launches no job, and only reads the fixed development challenge manifest. The caller must persist the manifest binding, source rows or their resolvable hashes, exact base/checkpoint/configuration identities, ordered inventory, records and summaries under a fresh output identity.

Each case starts from and restores a clone of the caller's fast state. Existing unrelated memory may remain as interference context; a near-miss/revision target already active in that state is explicitly unreachable. Query boundaries reset selection before and after each independent prompt; answer positions reuse the original prompt selection. Labels are used by support adaptation and scoring, never passed to prediction. Both base and reusable-weight identities are checked across each case.

## Endpoint definitions and denominators

**Near-miss:** teach the edited support, generate its own prompt answer, and regenerate the neighbour question. `preserved` is exact decoded-string equality to that neighbour's **actual cap-off greedy answer**, matching the v0 LS convention. The manifest's `neighbour_answer` is not used: in the source generator it can be copied from the edited row's old target rather than constitute a cap-off neighbour reference. `edit_exact` is reported separately, so trivial preservation following failed acquisition remains visible. Every evaluable case stays in the preservation denominator.

**Revision:** validate two strictly increasing versions with disjoint nonempty answer aliases. Teach the old support and check its answer, then teach the new support with the same fact ID. The primary original-prompt `revision_success` requires old-answer acquisition, latest-answer exactness, absence of the old alias on that prompt, old-record inactivity with the correct `superseded_by` link, and the new active record. Also report `latest_answer_success` independently, old acquisition, record IDs/flags, each paraphrase's latest/old answer flags, and the aggregate obsolete-answer reappearance count. Paraphrases are diagnostics separate from the primary prompt-level success; a caller can define a stricter all-query conjunction from the saved rows if the lead chooses that endpoint before execution.

**Composition:** require caller-supplied verification with `status="verified"`, exact `row_sha256=row_hash(row)`, and a nonempty `method` documenting label review. The evaluator checks the binding, not the truth of the review. Two distinct support facts must have active records. With `teach=True`, both are taught on the clone; with `teach=False`, they must already exist in the starting memory. Missing hops are unreachable. A unique literal occurrence of the first answer in the second support question defines a reviewed bridge template. The first query's **generated** text fills that template; gold bridge substitution is never used at runtime. A wrong/empty generated bridge remains a scored failed chain, not an unreachable case. The returned support IDs identify which records were available.

A successful two-query chain is not evidence of direct two-fact reasoning in one query. The separate `direct_composition` object defaults to unreachable because the manifest provides no direct question. To score it, the caller supplies `composed_prompt` and a matching `composed_prompt_sha256` in the verification. Report direct-query success separately from `chain_success`; do not call their pooled average composition accuracy. First-hop/second-hop alias checks currently use the stored o1/o2 labels, so acceptable aliases must be resolved during label review.

**Status policy:** rows are `ok`, `unreachable` or `resource_failure`. Ordinary wrong answers and non-resource unsuccessful updates remain evaluated cases. Missing/unverified inputs are unreachable; capacity/resource outcomes are resource failures and retain their work charges. Unexpected contract violations/nonfinite logits raise after clone restoration rather than inventing a score. Fatal exceptions need a caller-level failure artifact.

`summarize` returns planned, scored, successes, status counts, coverage and the success fraction over all evaluated cases. It refuses a non-boolean success field on an evaluated row. `full_inventory_fraction` is null unless every planned row was evaluable. This makes missingness explicit rather than silently dropping cases or reporting them as model failures. Empty inventories have null rates. No confidence interval or fresh-data claim is computed by this module.

## Record schema (version 1)

| Scope | Fields |
| --- | --- |
| Common case | schema_version, endpoint, case_id, source_row_sha256, dataset, status, optional reason, max_new_tokens, state_before, state_restored, wall_seconds |
| Query trace | prompt_sha256, prompt_tokens, generated, stopped_by, decode_steps, truncated, selection, returned_cost |
| Selection | record_ids, null_mass, best_score (null if nonfinite/unavailable), prompt_len |
| Update event | phase=learning, item_id, code, codes, returned_cost |
| Cost trace | events including cap-off/cap query identity; ledger_delta per learning/query/total; cost_policy |
| Near-miss | preserved, edit_exact, reference, edited_query, neighbour_query, update, explicit stored-label policy |
| Revision | revision_success, latest_answer_success, old_answer_acquired_before_revision, old_record_retired, new_record_active, old/new IDs, old_answer_reappearance_n, query_n, paraphrase_new_exact_fraction, before_revision, after_revision_queries, updates |
| Composition | chain_success, first_hop_exact, second_hop_exact, first_query, second_query, bridge_policy, support_record_ids, direct_composition, verification, interpretation |

Each `CostRecord` is preserved as its existing dictionary. Returned costs and shared-ledger deltas are distinct views, not added together. Cap-off references, rejected updates and all clone queries are charged; snapshots/ledgers are not rolled back together. This module does not repair omissions in upstream instrumentation or claim exact whole-training compute matching.

The CPU tests cover cap-off preservation, revision/retirement, charged resource rejection, overlapping aliases, generated-bridge errors and missing hops, unverified labels, mutation refusal/clone restoration, bridge ambiguity, actual inventory, and a real TinyBase/RevisionCap query-prefix reset with returned selection cost. Controlled-answer fixtures use a shorter decode cap; the public default remains 32.
