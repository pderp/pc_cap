# R1-77e — two-worker confirmatory queue

- Status: implemented and tested on CPU; final queue/freeze admission and GPU use remain owner work.
- Agent: Codex, Round24. Assigned in ongoing.md during the round, following commit2c63842.
- Changed: `scripts/r1_77_queue.py`; added `scripts/r1_77e_workers.py` and
  `tests/revision_v1/test_r1_77e_workers.py`. Installed source, driver and sealed backend remain untouched.
- Behavior: `--workers 2`, two cells from the same block, existing canonical locks, one shared
  process-time account, full active reservations, 1.65× solo wall ceilings, per-launch memory check
  with at least6GiB when another cell is outstanding. Workers drain before the next pair/block.
- Failure behavior: both process envelopes become durable; one failure does not abandon the
  completing worker. No subsequent cells launch after a known worker failure. Restart verifies/skips
  completed cells and retains all original resume/unknown-spend refusals.
- Repair discovered by concurrent execution: the unchanged durable cell writer assumes shared
  parents already exist. The queue now durably creates only common output/snapshot parents before
  workers start, avoiding a directory-creation race without touching active driver code.
- Budget meaning: sum of child-process durations, including overlap, never an independent budget
  per worker. Elapsed queue wall time is a separate field. Pending reservations defer a second cell
  until actual spend can be checked; effective process watchdogs respect the experiment deadline.
- Validation: `logs/r1_round24/r1-77e-tests.txt` and `r1-77e-serial-regression.txt`; actual TinyBase
  concurrency, success/failure, exception, resume/skip, memory, budget, block and timeout tests.
  Legacy queue tests require `--basetemp` under repository logs because the metadata reader correctly
  refuses temporary files outside the project. No production path restriction was loosened.
