## 1. Purpose and current evidence

Teach the reader that ordinary prose normally has no matching edit in its current memory. The null target trains the
retrieval decision; a preservation distribution constrains the model output even while soft training writes are possible.
This extends the existing locality and outside-memory factual null populations, whose query distributions differ
from prose.

The current text-null pilot uses eight text queries per episode, 512 windows and prefixes of 16/48/96 tokens. Its
recorded zsRE assay has firing 0/96 and ΔNLL −0.00000117634 nats on 4,064 positions, PPL ratio 0.9999988237. Its
100-edit development RET-GS is .96 on zsRE and .725 on CounterFact, versus .98/.795 in the paired reference streams.
That is a .02/.07 point reduction in RET-GS; “no cost to zsRE” is too strong if it means unchanged retention.
The pilot supports further testing, not full preservation certification. Reference seed variation does not replace
seed replication of this new recipe.

## 3. Prefixes and feature construction

Keep **(16, 48, 96)** for a directly interpretable pilot-family recipe. For each prefix:

- Feed only those tokens to the unchanged, cap-off base; no future token or answer label is a reader input.
- Save stable prompt-only observations, base/tap/encoder/tokenizer identities, the actual prefix length and padded
  bucket length, and one full-vocabulary last-position cap-off logit vector.
- Construct a null-target query (`target_record=-1`, packed index equal to memory length); do not append a support
  memory record and do not teach a factual answer.
- Preserve a distinct text provenance tag even if the existing role is `unrelated`. It must be possible to report text,
  locality and outside-memory factual errors separately.
- Cache teacher logits in float16 only as an explicit approximation, converted to float32 for the loss. Bind dtype
  and reference base; quantify approximation against a small full-precision development reference before admission.
  Rebuild if base/encoder/tokenizer/mask/prefix policy changes.

For 512 training windows there are **512 × 3 = 1,536 prefix queries and teacher distributions**, each from one base
forward. Logical input-token charge is **512 × (16 + 48 + 96) = 81,920**, not 1,536. Full window allocation is 65,536
tokens; the union of forwarded tokens is at most 49,152 for disjoint windows because the longest prefix is 96.
These are different denominators. A separate 128-window development bank adds 384 prefixes and 20,480 input positions.
Padded compute, cache bytes and construction wall/accelerator time must also be recorded.

The three chosen lengths do not cover all next-token prefixes from 1 through 127. Any later random-length or
length-stratified training is a separately declared ablation, not evidence already provided by the current pilot.

## 4. Episode composition and L2 class balance

Default fact episode: 64 memory records, eight queried records with one own prompt, one paraphrase and one locality
query each, plus eight outside-memory factual prompts. Add eight text prefixes sampled from the appropriate split.

| Population | Default queries | Target | Share of all 40 queries | Total L2 weight |
| --- | ---: | --- | ---: | ---: |
| own edit prompt | 8 | its memory record | 20% | 1/4 |
| paraphrase | 8 | its memory record | 20% | 1/4 |
| locality/near-miss | 8 | null | 20% | 1/6 |
| outside-memory factual | 8 | null | 20% | 1/6 |
| ordinary text | 8 | null | 20% | 1/6 |

There are 16 positive and 24 null targets. Current binary class balancing assigns total mass 1/2 to each class:
per-positive weight **1/32**, per-null weight **1/48**. Text is one third of the null queries, one fifth of all queries,
and one sixth of L2 mass. “Equal null populations” does not mean each has a quarter of the objective.

Generally, for Q+ positives and Q0 nulls, weight each positive by 0.5/Q+ and each null by 0.5/Q0; the existing implementation
uses uniform weights if one class is absent. Record actual counts and effective weight per role and per source domain.
Mixed-domain coverage repair can add an extra own/paraphrase/locality triple, and missing paraphrases can change counts.
Do not assume every episode has exactly 40 queries. Keep these adjustments visible in training and development logs.

Maintain the reference 300 steps × two episodes, memory size, learning rate, weight decay and selection rule for the
initial comparable recipe. If more text queries, a different memory distribution or per-role weighting is tried, give
it a separate ID and budget. Binary balancing alone does not balance CounterFact and zsRE.

## 5. L3 preservation target and normalization

For a text prefix x, let p0 be the frozen, same-base cap-off next-token distribution and pθ the cap-on distribution.
Preserve **KL(p0 || pθ)** over the full vocabulary at that prefix's last position, temperature 1, with gradients only
through pθ. This does not teach the true next token, a gold answer, an argmax pseudo-label or the entire 128-token window.
The preserved object is a distribution; L2 separately teaches abstention.

Current FastTrainer uses, with default coefficients all one:

`L_episode = sum(answer-prefix CE) + sum(locality-prefix KL) + sum(text-prefix KL) + class-balanced retrieval CE.`

Gradients sum across prefix groups and average across episodes in the batch. Logged answer/preservation losses divide
by their corresponding prefix counts; **the optimized objective is not those logged means**. With the default eight
locality prefixes, adding eight text prefixes increases preservation terms from 8 to 16. It changes effective L3 mass
relative to answer/retrieval, even if `w_preserve` is unchanged. An optional role-normalized preservation loss would be
a new intervention and requires a separately named recipe.

Outside-memory factual prompts currently use `unrelated_no_kl`: L2 null targets but no saved preservation logits.
Do not describe every null query as protected by L3. Report per-role KL sums, means, counts and coefficients, plus
query counts and answer-token prefix counts. The latter exceed the number of factual queries when answers span
multiple tokens.

## 6. Drift endpoint and units

For each fixed evaluation window of W tokens, predict positions **1 … W−1**, using the entire current prefix
`window[:j]` for position j. Reset cached selection before every prefix; select from that prefix and then score the
next token. Freeze edit memory throughout the assay. Ordinary prose has no answer boundary that justifies inheriting
a selection from a shorter prefix. A held-selection assay may be separately labeled as a diagnostic but cannot replace
this endpoint.

Compute NLL in nats as the sum of −log p(next token) divided by the **actual valid scored-position count N**.
Compute ΔNLL = mean NLL_on − mean NLL_off on exactly paired positions; PPL ratio = **exp(ΔNLL)**.
Do not use mean(exp(per-position difference)), a ratio of NLLs, bits, or 128K as the loss denominator.
For equal 128-token windows N = 127K: K=32 gives 4,064; K=64 gives 8,128; K=128 gives 16,256.
The separate R1-24 base-fidelity implementation scores 8,192 positions with its own lookahead construction; its
denominator must not be copied onto this sliding-prefix assay.

Firing probes currently use only three lengths per window: denominator **3K**, hence 96 for 32 windows.
A 0/96 observed probe rate is not proof of zero firing on all 4,064 scored prefixes. Report firing numerator/count,
hard-null definition, length strata, per-position NLL and optional firing-conditioned loss. Treat windows as correlated
clusters for uncertainty; no binomial claim about independent prefixes without justification.

Compare cap-on with the same condition's cap-off base to measure incremental cap drift. For continued bases also report
cap-off continued versus original, and cap-on continued versus original, on the same tokens. Keep original-base
common-reference LS and condition-specific incremental drift clearly labeled. Publish window/prefix inventory hashes,
N planned/scored, actual lengths, dataset, checkpoint/order/memory size, dtype, stop/selection policy, memory/base/parameter
hashes before and after, and the separate query ledger. Missing/nonfinite results are unavailable; do not discard
bad windows or tune on the final tail.

Use the DEC-033 provisional loss-increase ceiling .01 and base KL ceiling .001 where applicable; final drift/fidelity
scope and validation inventory must be explicitly frozen. Development's small subset is not the full endpoint
validation required by plan 9. Freeze the checkpoint cadence and evaluation budget before confirmation.
